## 考什么

侧栏搜索框(占位文案「搜索项目 / 会话 / 消息 (≥2 字符)...」)是**跨会话全局搜索**:一旦有词,
侧栏会话列表就被这个词按标题过滤(`composePanelSessions({query})`,过滤在 `UnifiedSidebar.jsx:1199`)。
问题不是"过滤"本身,而是**用户出不来**:清空只有一条代码路径(点搜索结果行),Escape 没绑在这个输入框上。
于是同一个搜索框里按 Escape,这一击会冒泡到会话级语义(`App.jsx:7639` 的 window 冒泡监听)——
**窗格里正有回合在跑时,它会把这个回合停掉**(`escAction.js:15` 有流即 `'stop'`;`:50` 焦点在 INPUT 时不让行)。

本轮补三件事:**出口**(Escape 清词 + P3 的 × / 说明行两个鼠标出口)、**别停回合**(有词时接管),
以及**接管别过头**(重命名框、授权卡、确认框这三处既有的 Esc 语义不许被新监听吃掉)。

| 用例 | 语义 | 修前预期 |
|---|---|---|
| **S1**(核心) | 搜索把列表过滤成只剩命中一条 → 在搜索框按 `Escape` → 搜索词清空 **且** 被过滤掉的会话重新出现 | **红**(Escape 没绑、冒泡到会话级语义;空闲态落在 `'arm'` = 看着没反应,搜索词留在框里) |
| **S2**(回归网) | 点**搜索结果行** → 搜索词清空、列表恢复、被点会话成为当前会话 | 绿(锁住 `handlePickHit` 的既有行为,防止 S1 的改动把它弄坏) |
| **S3**(核心·新缺陷) | 回合**正在跑**时,搜索框里**有词** → 按一次 `Escape` → 搜索词清空 **且回合不许被停** | **红**(有流时第一击即 `'stop'` ⇒ 搜索词留在框里、回合同样被停掉) |
| **S4**(阴性对照) | 回合**正在跑**时,搜索框里**没有词** → 按 `Escape` → 回合**照旧被停** | 绿(守"只在有词时接管",防止 P1 把既有的会话级 Esc 整段吞掉) |
| **S5**(新契约·P3) | 有词 → 搜索框出现 **×**(`data-cgui="sidebar-search-clear"`)→ 点它:清词 + 列表恢复;没有词时 × **不存在** | **红**(这个出口本来不存在;阴性那一半修前也绿) |
| **S5b**(新契约·P3 第二出口) | 有词 → 出现**过滤态说明行**(`sidebar-search-filter-hint`,「已按搜索词过滤 …」)→ 行内「**清空**」(`sidebar-search-clear-hint`)也能清词 + 列表恢复 | **红**(同上;**与 S5 的 × 是两个不同出口,两个句柄不许互相替代**) |
| **S5c**(新契约·P3 计数口径) | 搜索一个"3 条标题命中 + 1 条只有消息正文命中"的词 → 说明行的 N **只数标题那 3 条**(侧栏也只剩 3 行),而消息搜索仍能搜到第 4 条 | **红**(说明行本来就不存在) |
| **S6**(守卫·接管别过头) | 会话重命名输入框里按 `Esc` → **取消重命名**,且**搜索词必须原样留着** | 绿(重命名框自己消费了这一击;P1 落地后没"可编辑目标守卫"就会红) |
| **S7**(守卫·接管别过头) | 挂着**授权卡**时,焦点在**侧栏内的非可编辑元素**上按 `Esc` → **卡片被拒掉**,且搜索词不许被清 | 绿(`App.jsx:7618` 的 `escYieldCardId` 让行给卡片;P1 落地后没同样让行就会红) |
| **S9**(守卫·接管别过头) | **确认框**(⋯ →「删除会话」触发 `confirmDialog`)开着时,焦点在**侧栏内**按 `Esc` → **确认框被取消**,且搜索词不许被清 | 绿(确认框的监听在 `document` 冒泡、会话级监听在 `window`,中间没人截断;P1 落地后没 `[data-cgui-confirm]` 让行就会红) |

S3 的判据分三层,顺序刻意如此:**①** 搜索词清空(核心契约);**②** 停止键还在;**③(硬证据)**
放行假 CLI 的第二块,画得出来才算"回合真没被停" —— ①②都可能被时序骗过(停止请求是异步的),
③ 不会:回合真被停掉的话,那个进程已经没了,`<sid>.chunk` 放行再怎么写也不会有人读。
S4 用反向证据收尾:回合真被停掉后,再放行第二块也不该画出来。

**S5c 的 N 口径(契约)**:标题匹配 + **已加载项目** + **未归档**的会话数;
"只有消息正文命中"的会话**不算**(它走消息搜索那条路)。夹具为此专门造了 4 条会话(3 条标题含词 + 1 条只有助手回复含词)。

## 出口与守卫各用各的句柄(别混)

| 句柄 | 是什么 | 谁考 |
|---|---|---|
| `data-cgui="sidebar-search"` | 侧栏搜索框本身 | S1/S3/S4/S6/S7/S9 |
| `data-cgui="sidebar-search-clear"` | 搜索框里的 **×**(只在有词时出现) | **S5** |
| `data-cgui="sidebar-search-filter-hint"` | 过滤态说明行(有词时出现,含「匹配 N 条会话」) | **S5b / S5c** |
| `data-cgui="sidebar-search-clear-hint"` | 说明行里的「**清空**」—— 与 × 是**两个不同出口** | **S5b / S5c** |
| `data-cgui-confirm`(注意是 `dataset`,选择器写 `[data-cgui-confirm]`) | 确认框的宿主节点(`document.body` 下的独立挂载点) | **S9** |
| `data-cgui="stop-btn"` / `data-cgui="permission-card"` 类 | 停止键 / 授权卡相关 | S3/S4 / S7 |

## P1 的让行判据(开发代理定稿;S6/S7/S9 就是守它)

1. **可编辑目标守卫**:一击的目标是**可编辑控件**且**不是搜索框本身** ⇒ 不接管。
   (React 17+ 只在根容器挂一个监听、按 fiber 树模拟传播,所以重命名框里的
   `stopImmediatePropagation()` **挡不住**冒泡到侧栏根 —— 没这道守卫就会出现"取消重命名 + 顺手清搜索词",S6 红。)
2. **浮层让行**:权限/计划卡走 `App.jsx:7618` 同款纯函数 `escYieldCardId`;确认框看
   `document.querySelector('[data-cgui-confirm]')`。没这道守卫,焦点在侧栏内时这一击会被侧栏吞掉
   ⇒ 卡片拒不掉 / 确认框关不掉,S7、S9 红。

`<数据根>/home/fake-claude`(经 `R143_CTL` 注入用例)。

**端口**:从 `6700–6999` 里挑**当前空闲**的(用 `lsof` 实测,不是静态分段),硬拒 `6677 / 6689 / 6710`。
所以与别的套件(含并发跑的回归)不会撞端口;**但与别的写者同时跑会让 dev server 整页重载**
(vite 监听 `client/`),那种情况下的结论一律不算数 —— 见 PLAN §4.2 / TEST-PLAN §6。

## 边界(本套件不考的)

- 不覆盖接管提示 / 后台横幅(那是 r118 的考题);S3/S4/S7 只关心"这一击归谁"。
- 不考"点侧栏会话行是否清空搜索词"(方案 §3.4 决定不做)。
- S6/S7/S9 是**守卫**不是新功能:S6 只验"重命名被取消 + 搜索词没动",不验重命名本身的保存/落盘;
  S7 只验"卡片被拒掉 + 搜索词没动",不验拒绝之后工具调用怎么收场;
  S9 只验"确认框被取消 + 搜索词没动",**不点确定、不真删会话**(所以它没有任何破坏性副作用)。
- S7 的卡片靠夹具的 `can_use_tool` 控制请求造出来(报文格式抄自
  `tests/acceptance/stripfold-20260913/helpers/fake-claude.mjs` 的可用先例)。**若卡片压根没出现**,
  先怀疑夹具/协议这一层(看 `<sid>.phase` 有没有走到 `permission`),不是产品 bug —— TEST-PLAN §3.4 已预登记。
- S9 的确认框走**产品自带**的入口(会话 ⋯ →「删除会话」→ `confirmDialog`),不需要产品为测试加任何东西;
  它的 Esc 监听见 `utils/confirmDialog.jsx:17-23`(**document 冒泡**),所以只要焦点在侧栏内,
  P1 截断就会让它关不掉 —— 这正是 S9 守的东西。
- 夹具侧栏可见性的前提:夹具项目在**主仓路径**下才进侧栏(`PROJECT.md:1902` 记过 worktree 会隐藏它)。
- 每条跑回合的用例各用一条**专用**夹具会话(S3 `POOL[0]` / S4 `POOL[1]` / S7 `POOL[3]`)。
  回合跑完后应用会改写会话标题,所以"被过滤见证"另用从不跑回合的会话(S3 `POOL[5]` / S4 `POOL[4]`)——
  别把这两个角色合并到同一会话上。
- S5c 用一组**专用**夹具会话(`CNT` 3 条 + `CNT_MSG_ONLY` 1 条),不被别的用例使用;
  它的搜索词是 `R143CNTMARK`(夹具导出的 `CNT_TOKEN`)。

## 与 r118 老助手的关键差别(别改回去)

搜索结果行是原生 `<button class="sidebar-item">`(`App.jsx:1602` 起),**这个元素没有 `role` 属性**;
侧栏会话行才是 `<div role="button" data-cgui="session-row" class="sidebar-item">`(`App.jsx:1754/:1756`)。
两个元素的**可访问名都含会话标记**,所以:

| 定位器 | 命中搜索结果行 | 命中侧栏会话行 |
|---|---|---|
| `getByRole('button', { name: /标记/ })` | **是** | **是**(显式 `role=button`)⇒ **重合,这就是老助手点错的那一下** |
| `[role=button].sidebar-item` | 否(没有 `role` 属性) | 是 |

老助手写的是"名字里含标记的第一个按钮",全局搜索有 220ms 防抖 + 一次 `/api/search` 往返,而侧栏会话行是同步渲染的
⇒ `.first()` 会落到会话行 ⇒ 会话打开了、搜索词却留在框里 ⇒ 侧栏被这个词永久过滤(2026-09-16 的假红根因)。
本套件的 `helpers/ui.mjs` 因此把搜索结果行钉在 `<button>` 标签上,并**优先使用产品句柄
`data-cgui="search-hit"`**(REVIEW-PLAN-r143 §7-1 要求开发代理给命中行加的那个句柄;句柄落地后这个双选择器
自动切过去)。**不要**把定位器改回 `[role=button].sidebar-item` —— 那正是会话行。
