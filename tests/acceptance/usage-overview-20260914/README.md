# usage-overview-20260914 · 用量总览冷启动验收(U1~U10 + UI-1/UI-2)

验的是 `.devflow/BRIEF-20260914-usage-cold.md` §4 的判据表:每次重启 GUI 后打开用量界面
都要等 40 秒。根因是 `usage-stats.js` 的缓存只在内存 + 冷路径无合流 + 预热与首次打开互相踩。
本套件只按 BRIEF 的判据写,**不看实现**(修法只动 `usage-stats.js` + 两处前端,黑盒口径)。

## 怎么跑

```sh
cd tests/acceptance/usage-overview-20260914

./run-isolated.sh          # U1~U7 + U10(合成夹具,整套约 70 秒)
./run-isolated.sh --ui     # UI-1/UI-2(浏览器层,约 10 秒;前提见下)
./run-isolated.sh --real   # U8(只读软链真实 ~/.claude/projects,约 1~2 分钟,会真读 6GB+)
./run-isolated.sh --u9     # U9(回归既有三个套件;在 /tmp 复印件里跑,不动原目录)
```

`--ui` 跑的是**构建产物**(浏览器加载 `client/dist`,不是源码),所以改了前端之后要先:

```sh
cd client && npx vite build     # 只要 client/dist 比 client/src 旧,ui-runtime.mjs 会当场报环境错
```

端口:自动从 6700 起挑空闲,**硬拒用户正在用的 6677 / 6689**(`resolvePort` 里断言,
脚本里再拒一次)。`HOME` 一律指到本套件 `.artifacts/runtime-data/home*`;
除 U8 的只读软链外,不写用户的 `~/.claude`、`~/.claude-gui` 一个字节。
杀进程只按记录下来的 pid(`process.kill(pid)`),没有 `pkill -f` 这类按名字杀的写法。

## 夹具

- 合成夹具 1036 个 jsonl / 12.3MB(24 项目 × 43 会话 + 4 个子代理转写),生成 0.19 秒,
  清单落在 `.artifacts/runtime-data/fixture-manifest.json`,对得上就复用(改夹具要 `FIXTURE_VERSION +1`)。
- **复用前先对账,防夹具漂移**:清单里的 `stats.files / stats.bytes` 与磁盘实测不符就重造夹具并
  打印原因。U3b 会就地改夹具(追加一行,finally 里按长度截断还原),进程若挂在两步之间,夹具就
  永久多一行 —— 之后每次跑都是无法解释的假红。实测:追加 82 字节 → `清单对得上但磁盘已漂移
  (实测 1036 文件 / 12904663B,清单 1036 / 12904581)` → 重造。**只比文件数抓不到追加/截断,必须比
  字节数**。
- **期望值是手算的,不是拿产品算的**:`helpers/fixtures.mjs` 在写字节的同一个循环里登记
  `total / byModel / byProjectRows / byDayRows`,并显式标出「哪些记录是重复副本、为什么不该被计入」:
  跨文件重复 `message.id` 三种形态 —— ①先出现的小副本(630 < 6300,应留后者)
  ②先出现的大副本(7000 > 6300,应留前者,"不是先到先得")③逐字节相同的抄本(只算一次)。
  另有无 `message.id`(必须直接计入)、无 `timestamp`(落 byDay 的 `unknown`)、
  非 assistant 行、无 usage 行、坏 JSON 行各一。
- 单次冷扫实测 165~300ms(随磁盘缓存冷热波动)。"秒回"阈值的分母取**同一轮里两个数里的较小值**:
  进程内探针的冷扫 `scanMs` 与服务端自己的冷路径请求 `coldMs` —— 后者与 U2 量的是同一条 HTTP
  路径,拿它当分母才不会因为探测口径不同而放松判据(实测 `coldMs` 常比 `scanMs` 小 20~30%)。
- **逐行锚点**:`byProject`(24 个项目,响应截断到 20 行)与 `byDay`(5 天 + unknown)的每一行
  `input/output/cacheRead/cacheWrite/calls` 都手算。只锚 total + byModel 时,"按项目/按天张冠李戴"
  能同时骗过 U4(往返一致 = 两边一起错)与 U6a(行数对、日期序列对)。实测见下文「判别力对照」。

## 每条为什么这么测(容易误判的点)

- **U1 用"同一对象引用"而不是计时**:N 个并发各扫一遍时 I/O 会交错,墙钟只放大 1.9~3.4 倍
  而不是 N 倍(实测 5 并发 566~629ms vs 单发 166~296ms),计时判不出合流;对象引用是二值信号。
  **U1 是合流的权威判据,U1b 只是 HTTP 层佐证 —— 别把结论压在 U1b 的计时上。**
- **U1b 的分母必须同口径**(2026-09-14 改):旧版分母是**另一个进程**里的单次冷扫(探针 `scanMs`),
  分子是 HTTP 三并发 —— 两个测量各自 ±30%~50% 抖动且互不相关,同一份代码 7 次跑出
  0.83 / 1.53 / 0.87 / 1.34 / 1.08 / 1.02×,阈值 1.5× 正好压在分布中间。现在分母换成"另一台
  同样无缓存实例上的一次 HTTP 冷请求",两者只差"并发数"这一个变量,分布立刻收窄。
  另外内容断言(三发响应逐字节相等,含 `meta.scannedAt`)在未合流时必然红:三次重算各产一个
  `scannedAt`,差几毫秒就是差几毫秒。
- **U3a 需要"没发生"的证据**:数据不变时"重扫了"和"没重扫"结果一模一样,所以不比对数据,
  而是看 ①`meta.scannedAt` 有没有前进 ②服务端自身 CPU 有没有涨(两次独立信号)。
  CPU 口径踩过两个坑:`ps -o cputime` 连 wait 过的子进程一起算(实测基线 35 秒级,断言会变空),
  且 macOS 格式是 `MM:SS.ss` 只一个冒号(按 `HH:MM:SS` 解会差 100 倍)。已改用 `ps -o time=`
  并正确解析(`helpers/runtime.mjs` 的 `cpuMs`)。
- **U3a 的观测窗口必须挪出启动后的头 13 秒**(2026-09-14 改):实测实例启动后每秒烧
  10~60ms CPU(第 10 秒还有个 320ms 尖峰,是预热定时器那次调用),3 秒窗口合计 30~90ms ——
  而上限公式的地板当时只有 30ms,窗口落在噪声带里就是"在无关噪声上翻红"。现在:窗口从
  `spawnedAt + 13s` 起算,先量一段同样长的**空闲基线**,上限取
  `max(150ms, 一次全扫 CPU/2, 基线+60ms)`。实测(本机):基线 Δ0ms、观测 Δ0ms、上限 150ms、
  真重扫的 CPU Δ290~310ms → 2 倍分离度。**`scannedAt` 那条从这个窗口起算更早**:
  它从首次(磁盘回放)请求那一刻算起,所以等待的那 13 秒里如果有人乱扫,也逃不掉。
- **U2 的阈值取"一次全扫的一半"**:不写死毫秒数,免得换机器就飘;分母每次现测(见上)。
  即使实现选择"先走一次目录签名检查再回值"(约 60~80ms),也仍然在阈值内。
  修前实测这一发是 156~200ms(阈值 83~111ms)→ 红得很明显,不会是边界噪声。
- **U4 只测往返,不断言算账对错**:算账对不对由 U6a 用**独立手算表**兜住(两份期望不共源);
  U4 若单独看,修前也绿(没有持久化时两次都是现算)。
- **U5 三条一起看**:①不抛错 ②退回冷扫的数对 ③坏文件被覆盖成合法内容(修前"原样留着"也是红)。
- **U7 修前只在 meta 上红**:它的价值在"修后必须仍绿" —— 缓存目录不可写不许把 `/api/usage` 变成 500。
- **UI-1 打桩、UI-2 不打桩**:显示规则只取决于服务端给的 `meta.stale`,打桩能给"true/false 一对"
  最干净的输入;**"广播→刷新"是链路行为**(服务端重算 → WS 广播 → 页面监听 → 静默重取),
  任何一环打桩都等于把要验的东西换掉,所以 UI-2 真实例、真 WS、真重扫,只观察界面。
- **UI-2 的状态用"时间线"判,不用手速**:面板的中间态只活 250ms 左右(重扫一落地就没了),
  靠某一刻去截图必然与它赛跑。所以在页面脚本一开始就挂 MutationObserver,只在状态变化时记一条
  `{loading, stale}`;于是"那句提示**出现过**"与"loading 之后再没闪过"都变成对时间线的判定。
  再配上"探针模型出现在界面上"+"面板发起了第二次 `/api/usage`",三条独立证据指向同一条链路。

## 没覆盖 / 拿不准

1. **`meta.stale` 在冷路径必须存在且为 `false`**:BRIEF §3.3 只写了"响应加 meta",没说冷路径
   能不能省。本套件按"用 meta 区分磁盘回放与现算"的目的断言**冷路径也要给 meta**。
   若实现选择冷路径不给 meta,U5/U6d/U7 会报红 —— 那属于口径分歧,不是产品缺陷(已在报告里列明)。
2. **`scannedAt` 的语义**:U3a 假定"重算会让 scannedAt 前进、不重算则不变"。若实现把 scannedAt
   定义成别的时刻(例如只表示磁盘写入时刻),U3a 的这条信号会失真;但同一用例里 CPU Δ 那条独立成立。
3. **U8 量的是"磁盘缓存已存在 → 重启 → 首请求"**(相位 1 先真扫一次造缓存,相位 2 测重启)。
   BRIEF 写的"修后冷启动首请求 <1s"如果指的是"**首次**运行、无任何缓存",那它不可能 <1s
   (没缓存就只能现扫),所以按用户的真实痛点口径解释,README 里明说。
4. **U9 三条的实测**(2026-09-14 02:03 / 02:06):
   - `pricing-usage-20260911`:**不可运行** —— 目录里只剩 `.artifacts/probe/ui-probe*.mjs`,
     没有 `run-isolated.sh` 也没有 spec。记为红(不冒充绿、也不算跳过)。
   - `theme-usage-20260912`:绿,`--grep TU-5` 18/18 通过(4.4 分钟)。默认只跑这一组是因为
     它与本改动同面(用量卡);全量跑 `U9_TU_GREP= ./u9-regression.sh`。
   - `slowload-20260912`:**原地跑是绿的,红只出在 /tmp 复印件口径**(2026-09-14 03:09 定性)。
     · 原地:`cd tests/acceptance/slowload-20260912 && ./run-isolated.sh` → **15/15 全绿、退出码 0**,
       首跑即过;同一套件里"大项目 200 文件"那档冷进程耗时 99.7ms(门槛 250/600ms 级),索引落盘
       等待没有任何超时。
     · 复印件(`u9-regression.sh`):稳定红在同一行 `slowload.spec.mjs:100`
       `索引文件 -slowload-20260912-big.json 在 5000 ms 内没有落盘(基线 mtime=null)`。
     · **判据(为什么判它是复印件口径的问题,不是既有产品红)**:
       ① 同一份数据、同一份代码,原地绿、复印件红 —— 差异只在"跑在哪";
       ② 两边的大项目目录一模一样(都是 202 文件 / 20MB),不是数据量差异;
       ③ 复印件自己留下的现场里,服务端只写了 1 文件那档的画像(`nosidecar files=1 wrote=370B`),
          200 文件那档始终没写 —— 而复印件那个 19MB 夹具文件比原地的**小 1800 字节**,
          说明复印件那份夹具本身就不是原地那份(复印件生成的夹具与原地的确有差);
       ④ 本改动完全不碰 session-index(只动用量缓存)。
     · **没查清的部分**:复印件为什么生成出不同的夹具、以及为什么大项目画像没写出来,没有继续追
       (那是 u9 复印件 harness 的事,超出本套件范围)。**结论只到"原地是绿的"这一层** ——
       判据表里 U9 记录的红按复印件口径理解,别当成产品缺陷。
5. **前端只剩两条没验**:①文案的**位置/样式**(只验了"出现/消失"与"不闪 loading",没验它落在
   「总览」标题旁边、字色是否合适)②`cgui:chat-done` 那条同源的静默刷新(与广播走同一个函数,
   没单独验)。
6. **UI-2 依赖一个 250ms 量级的窗口**:面板首帧的 stale 状态只活到后台重扫落地。用时间线判定
   已经消掉了"手速"这个变量,但如果哪天重扫快到几毫秒就落地,这条会变成假红 —— 那时该改的是
   让夹具更慢,不是删断言。
7. **不覆盖增量扫描/分时段计价**:前者 BRIEF 明确不做;`byPeriod` 桶只做往返比对,没有手算锚点
   (它的分桶随计价规则走,手算成本高、收益低 —— 已用最便宜的方式覆盖)。
8. **夹具对账只比文件数与字节数**:内容被等长替换(同字节数、同文件数)检测不到。本套件的漂移
   来源只有 U3b 的追加/截断,这两种都改字节数,所以够用。
9. **U3a 的上限会吸收"持续的背景重活"**:基线窗口若本身就烧着 CPU,上限会跟着抬到"基线+60ms"。
   这是刻意的(噪声随机器变,写死地板就会在别的机器上假红);代价是"一直烧、烧得和基线一样多"
   的重活测不出来 —— 但那种情况下 `scannedAt` 那条仍在看着。
10. **并发量级**:U1/U1b 用 5/3 并发。真机上"关面板再打开"可能更密集,但合流是无状态的,
    并发数不影响结论。
